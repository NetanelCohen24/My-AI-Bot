# Stockout Radar · חדר בקרה טקטי

אפליקציית Web (React + Tailwind) לאנליסט מכירות וסחר. מזהה **מלאי רפאים** וחריגות מכירה ברמת סניף × מוצר, ומפיקה רשימת משימות לשטח מוכנה לוואטסאפ/מייל. כל העיבוד מתבצע בדפדפן — הנתונים לא נשלחים לשום שרת.

## הרצה

```bash
cd stockout-radar
npm install
npm run dev      # http://localhost:5173
npm test         # בדיקות למנוע הזיהוי, לפרסר ולמחולל המשימות
npm run build    # בנייה סטטית ל-dist/ (Netlify / כל שרת סטטי)
```

## קלט

CSV / Excel (אפשר כמה קבצים יומיים יחד; קבצים חדשים מצטרפים לקיימים). כותרות מזוהות אוטומטית בעברית או באנגלית:

| שדה | דוגמאות לכותרת | חובה |
|---|---|---|
| תאריך | `תאריך`, `date` (DD/MM/YYYY, ISO, תאריך Excel) | ✔ |
| קוד סניף | `קוד סניף`, `store_id`, `branch` | ✔ |
| ברקוד/מק״ט | `ברקוד`, `מק"ט`, `sku`, `barcode` | ✔ |
| כמות מכירה יומית | `כמות מכירה יומית`, `qty`, `units` | ✔ |
| יתרת מלאי במערכת | `יתרת מלאי`, `inventory`, `on_hand` | ✔ |
| שם רשת / שם מוצר / שם סניף / אזור | `שם רשת`, `שם מוצר`, `שם סניף`, `אזור` | רשות |

כפתור **"טען נתוני דמו"** מייצר 63 ימים × 20 סניפים × 12 מוצרים עם 20 תרחישי קיצון: 7 מלאי רפאים, נפילות חדות, קפיצות ביקוש (גל חום/מבצע), חוסר אמיתי במלאי, ותקלת קופות בסניף שלם.

## לוגיקת הזיהוי (`src/lib/engine.js`)

- **מלאי רפאים** — מלאי POS מעל הסף (ברירת מחדל 10), רצף של 3–5 ימי אפס מכירות שמסתיים ביום האחרון, וממוצע חיובי ב-28 הימים *שלפני* הרצף. מגן פואסון: `1 − e^(−ממוצע×ימים) ≥ 99%`, כדי שמוצר איטי שבמקרה לא נמכר 3 ימים לא יוצג כרפאים.
- **חריגות (Z-Score)** — ממוצע נע 28 יום × מקדם יום-בשבוע (חמישי/שישי גבוהים, שבת נמוכה), וסטיית תקן של השארית. נבדקים Z יומי ו-Z מצטבר ל-3 ימים. נפילה ≤ −2σ = ירידה חריגה; ≤ −3σ = קריטית; ≥ +2σ = קפיצת ביקוש. נדרש גם פער מהותי ביחידות, למניעת התראות רעש.
- **אזל מהמלאי** — מלאי 0 במערכת ואין מכירות, למרות ממוצע חיובי.

כל הספים ניתנים לכיוון בלחצן **"ספים"** (נשמרים בדפדפן).
